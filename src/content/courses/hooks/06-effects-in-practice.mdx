Effects are powerful and easy to misuse. This lesson is about using them well: fetching data correctly, and **not** using them when something simpler works.

<Concept name="Fetching data, and the race condition" id="fetching">

Here's a product page that loads the selected product. The fake API answers **Coffee slowly** and **Tea quickly**. Click **Tea** right after the page loads, then wait.

<ReactPlayground height={360}>

```jsx file=/App.js
import { useEffect, useState } from "react";
import { fetchProduct } from "./api";

export default function App() {
  const [id, setId] = useState(1);
  const [product, setProduct] = useState(null);

  useEffect(() => {
    setProduct(null);
    fetchProduct(id).then((data) => setProduct(data)); // no protection!
  }, [id]);

  return (
    <>
      <button onClick={() => setId(1)}>Coffee</button>{" "}
      <button onClick={() => setId(2)}>Tea</button>
      <p>Selected: #{id}</p>
      {product ? <h2>{product.name}</h2> : <p>Loading…</p>}
    </>
  );
}
```

```js file=/api.js
const PRODUCTS = { 1: { id: 1, name: "Coffee" }, 2: { id: 2, name: "Tea" } };

// A fake network: Coffee takes 1.5 seconds, Tea 0.3
export function fetchProduct(id) {
  const delay = id === 1 ? 1500 : 300;
  return new Promise((resolve) => setTimeout(() => resolve(PRODUCTS[id]), delay));
}
```

</ReactPlayground>

"Selected: #2" but the heading says **Coffee**. Tea's response arrived first; then Coffee's slow response arrived and overwrote it. That's a **race condition**: responses can come back in any order.

The fix is the cleanup. Each effect run gets its own `ignore` flag, and when the id changes, the cleanup marks the old request as stale:

```jsx file=App.jsx
useEffect(() => {
  let ignore = false;
  setProduct(null);
  fetchProduct(id).then((data) => {
    if (!ignore) setProduct(data);
  });
  return () => {
    ignore = true; // this request is out of date
  };
}, [id]);
```

With real `fetch`, you can also cancel the request itself: create an `AbortController`, pass `{ signal: controller.signal }` to `fetch`, and call `controller.abort()` in the cleanup.

<Callout type="tip">
Fetching in effects works, but real apps usually use a data library (TanStack Query, the React Ecosystem course) or a framework's loaders. They handle races, caching, retries and loading states for you.
</Callout>

</Concept>

<Concept name="You might not need an effect" id="not-needed">

The most common effect bug is an effect that shouldn't exist. If there's no **outside system** involved, you almost certainly don't need one.

<Compare
  wrong="Derived state in an effect: an extra render, and a moment where total is wrong"
  right="Calculate it during render"
  wrongFile="Cart.jsx"
  rightFile="Cart.jsx"
>

```jsx
const [total, setTotal] = useState(0);
useEffect(() => {
  setTotal(cart.reduce((s, l) => s + l.price * l.qty, 0));
}, [cart]);
```

```jsx
const total = cart.reduce((s, l) => s + l.price * l.qty, 0);
```

</Compare>

| You want to… | Instead of an effect… |
| --- | --- |
| compute something from props or state | calculate it during render (`useMemo` if slow) |
| reset state when a prop changes | give the component a `key` |
| react to a user action (submit, buy) | do it in the event handler |
| notify the parent of a change | call the parent's callback in the same handler |
| chain "when A changes, set B, then C" | compute B and C in the handler that changes A |

</Concept>

<Concept name="Infinite loops" id="loops">

An effect that sets state which is also one of its dependencies (or that has no dependency array) can loop forever: render → effect → set state → render → effect…

```jsx file=Loop.jsx
useEffect(() => {
  setCount(count + 1);   // changes count…
}, [count]);             // …which re-runs the effect, forever
```

Also watch out for **objects and functions created during render** in the dependency array: they're new every render, so the effect runs every render. Move them inside the effect, or memoize them.

</Concept>

<Concept name="useEffectEvent: read the latest values without re-syncing" id="effect-event">

Sometimes an effect needs a value that should **not** cause a re-sync. A chat connection should reconnect when `roomId` changes, but not when the `theme` used for its notification changes. **`useEffectEvent`** (stable in React 19.2) pulls that logic out into an **effect event**: a function that always sees the latest props and state, but isn't a dependency.

```jsx file=ChatRoom.jsx
import { useEffect, useEffectEvent } from "react";

function ChatRoom({ roomId, theme }) {
  const onConnected = useEffectEvent(() => {
    showNotification("Connected!", theme); // always the current theme
  });

  useEffect(() => {
    const connection = createConnection(roomId);
    connection.on("connected", () => onConnected());
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]); // theme isn't a dependency: changing it doesn't reconnect
}
```

Only call effect events from inside effects, and don't pass them to other components.

</Concept>

<HowItWorks title="Why each effect run has its own ignore flag">

`let ignore = false` is declared **inside** the effect, so every run creates a fresh variable, captured by that run's `.then` callback and that run's cleanup (closures!). When `id` changes, React calls the old run's cleanup, which sets the **old** `ignore` to true. The old request's callback checks its own `ignore`, sees `true`, and does nothing. The new run's flag is still `false`, so its response is used.

</HowItWorks>

Switching from Coffee to Tea quickly shows Coffee, because the slow Coffee response arrives last. Make the page always show the product that was picked **last**, by ignoring stale responses in the effect's cleanup.

```jsx starter file=/App.js

import { fetchProduct } from "./api";

export default function App() {
  const [id, setId] = useState(1);
  const [product, setProduct] = useState(null);

  useEffect(() => {
    setProduct(null);
    fetchProduct(id).then((data) => setProduct(data));
  }, [id]);

  return (
    <>
      <button onClick={() => setId(1)}>Coffee</button>{" "}
      <button onClick={() => setId(2)}>Tea</button>
      {product ? <h2>{product.name}</h2> : <p>Loading…</p>}
    </>
  );
}
```

```js starter file=/api.js
const PRODUCTS = { 1: { id: 1, name: "Coffee" }, 2: { id: 2, name: "Tea" } };

import { act, fireEvent, render, screen } from "@testing-library/react";
import "@testing-library/jest-dom";
import App from "./App";

const wait = (ms) => act(async () => {
  await new Promise((resolve) => setTimeout(resolve, ms));
});

test("loads the first product", async () => {
  render(<App />);
  await wait(400);
  expect(screen.getByRole("heading")).toHaveTextContent("Coffee");
});

test("a slow old response never overwrites the newer one", async () => {
  render(<App />);
  fireEvent.click(screen.getByRole("button", { name: "Tea" }));
  await wait(100);
  expect(screen.getByRole("heading")).toHaveTextContent("Tea");
  await wait(400);
  expect(screen.getByRole("heading")).toHaveTextContent("Tea");
});
```
