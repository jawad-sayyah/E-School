**Hooks** are functions whose names start with `use` that let a function component "hook into" React features: state, effects, context, refs and more. You've already used `useState` and `useRef`. This course covers **every** built-in hook, and how to write your own.

<Concept name="Before hooks: class components" id="classes">

Until 2019, a component that needed state had to be a **class**. Here's the same counter both ways:

<Compare
  wrong="A class: this, binding, and the logic split across lifecycle methods"
  right="A function with hooks: the same behavior in a few lines"
  wrongFile="Counter.jsx"
  rightFile="Counter.jsx"
>

```jsx
class Counter extends Component {
  state = { count: 0 };
  componentDidMount() {
    document.title = `Clicked ${this.state.count} times`;
  }
  componentDidUpdate() {
    document.title = `Clicked ${this.state.count} times`;
  }
  render() {
    return (
      <button onClick={() => this.setState({ count: this.state.count + 1 })}>
        {this.state.count}
      </button>
    );
  }
}
```

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    document.title = `Clicked ${count} times`;
  }, [count]);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

</Compare>

Classes had three big problems that hooks solve:

1. **Logic was split by lifecycle, not by meaning.** Setting up a subscription went in `componentDidMount`, updating it in `componentDidUpdate`, and cleaning it up in `componentWillUnmount`. One feature lived in three places.
2. **Reusing stateful logic was awkward.** Sharing "track the window width" between components needed wrappers (higher-order components, render props) that piled up. With hooks, it's one function: `useWindowWidth()`.
3. **`this` was confusing**, and forgetting to bind a method was a classic bug.

You'll still meet classes in older code (and error boundaries still need one), so it helps to recognize them.

</Concept>

<Concept name="The Rules of Hooks" id="rules">

Hooks only work if you follow two rules:

1. **Only call hooks at the top level** of a component or custom hook. Not inside `if`, loops, nested functions, or after an early `return`.
2. **Only call hooks from React functions**: function components and custom hooks (functions whose names start with `use`). Not from regular functions or event handlers.

<Compare
  wrong="A hook inside a condition: on some renders it's skipped"
  right="Always call the hook; put the condition inside it, or after it"
  wrongFile="Search.jsx"
  rightFile="Search.jsx"
>

```jsx
function Search({ enabled }) {
  if (!enabled) return null;
  const [query, setQuery] = useState("");
  // ...
}
```

```jsx
function Search({ enabled }) {
  const [query, setQuery] = useState("");
  if (!enabled) return null;
  // ...
}
```

</Compare>

The official ESLint plugin, `eslint-plugin-react-hooks`, checks both rules (and effect dependencies) as you type. Every serious React project has it on.

</Concept>

<HowItWorks title="Why the order matters">

React doesn't know your hooks by name. It stores each component's hook data in a **list**, in the order the hooks are called. On the first render, `useState("")` creates slot 1, `useState(1)` slot 2, `useEffect` slot 3. On every later render, React walks the same list in the same order: the first `useState` call gets slot 1's value, and so on.

If a hook is skipped on some render (because it's inside an `if`), every hook after it reads the **wrong slot**: your `qty` might get the search text. React detects this and throws "Rendered fewer hooks than expected". The rules exist so the order is always the same.

</HowItWorks>
