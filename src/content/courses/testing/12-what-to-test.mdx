You can't test everything, and you shouldn't try. Good teams spend their testing time where bugs are **likely** and **costly**, and test **behavior** that users and other code rely on.

<Concept name="Test these" id="test-these">

- **Business rules and money:** totals, discounts, taxes, shipping thresholds, stock limits. Bugs here cost real money.
- **State logic:** reducers, custom hooks, stores. Dense logic, easy to test.
- **User flows that matter:** adding to the cart, checkout, sign-in, the forms people must fill in.
- **Every state a user can see:** loading, empty, error, success, disabled.
- **Edge cases and past bugs:** each fixed bug gets a regression test.
- **Accessibility basics:** names, labels, roles (your queries already do this).

</Concept>

<Concept name="Skip these" id="skip-these">

- **Implementation details:** state variable names, which hook was used, internal function calls, CSS classes.
- **Third-party code:** don't test that React renders or that React Router routes; test *your* use of them.
- **Trivial code:** a component that only passes props through, a constant, a re-export.
- **Exact markup snapshots of whole pages:** they break on every change and get approved without reading (next lesson).
- **The same behavior many times** at different levels: one solid test beats five overlapping ones.

</Concept>

<HowItWorks title="The testing trophy">

For front-end apps, many teams follow the **testing trophy** (Kent C. Dodds): a base of **static checks** (TypeScript, ESLint) that catch typos and type errors for free; a thin layer of **unit tests** for pure logic; the biggest layer of **integration tests** (components rendered with their real children, context and mocked network, via Testing Library and MSW); and a few **end-to-end tests** for critical flows. Integration tests give the most confidence per minute spent, because they test what users actually do without the cost of a real browser.

</HowItWorks>

<TestExercise
  id="test-shipping-cost"
  title="Test what matters: shipping cost"
  hints={[
    "Test the threshold from both sides: just under $50 pays, exactly $50 ships free.",
    "Check express is always $9.99, even over $50.",
    "Check an empty cart (total 0) costs standard shipping, not free.",
  ]}
>

`shippingCost(total, method)`: standard shipping is **$4.99**, free from **$50**; express is always **$9.99**. Write the few tests that matter (the boundaries and each method) and catch every buggy version.

```js code file=shipping.js
function shippingCost(total, method = "standard") {
  if (method === "express") return 9.99;
  return total >= 50 ? 0 : 4.99;
}
```

```js starter
test("standard shipping for a small order", () => {
  expect(shippingCost(20)).toBe(4.99);
});
```

```js bug title="Express is free over $50 too" hint="Check express shipping on a big order."
function shippingCost(total, method = "standard") {
  if (total >= 50) return 0;
  if (method === "express") return 9.99;
  return 4.99;
}
```

```js bug title="Threshold uses >" hint="What about an order of exactly $50?"
function shippingCost(total, method = "standard") {
  if (method === "express") return 9.99;
  return total > 50 ? 0 : 4.99;
}
```

```js bug title="Standard is never free" hint="Check a standard order of $60."
function shippingCost(total, method = "standard") {
  if (method === "express") return 9.99;
  return 4.99;
}
```

```js solution
describe("shippingCost", () => {
  test("standard: $4.99 under $50, free from $50", () => {
    expect(shippingCost(49.99)).toBe(4.99);
    expect(shippingCost(50)).toBe(0);
    expect(shippingCost(60)).toBe(0);
  });
  test("express is always $9.99", () => {
    expect(shippingCost(20, "express")).toBe(9.99);
    expect(shippingCost(80, "express")).toBe(9.99);
  });
});
```
