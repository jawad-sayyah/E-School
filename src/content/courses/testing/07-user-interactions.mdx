Components react to users: typing, clicking, tabbing. Tests should do the same, then check what changed on screen. Some changes happen **later** (after a fetch or a timer), so tests also need to **wait**.

<Concept name="user-event: interact like a real user" id="user-event">

In a real project, simulate interactions with **`@testing-library/user-event`**. It fires the full sequence a real user causes (focus, keydown, input, keyup, click…), so it catches bugs that a single synthetic event misses:

```jsx file=Search.test.jsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("typing filters the menu", async () => {
  const user = userEvent.setup();
  render(<Menu />);

  await user.type(screen.getByRole("searchbox", { name: "Search" }), "tea");
  await user.click(screen.getByRole("button", { name: "Hot only" }));
  await user.keyboard("{Escape}");

  expect(screen.getAllByRole("listitem")).toHaveLength(2);
});
```

Every `user.*` call is async: always `await` it. Create one `user` per test with `userEvent.setup()`.

<Callout type="warn">
The exercises on this site run inside Sandpack, whose test runner can't run user-event, so they use **`fireEvent`** from Testing Library instead: `fireEvent.click(button)`, `fireEvent.change(input, { target: { value: "tea" } })`. It dispatches a single DOM event. In your own projects, prefer user-event.
</Callout>

</Concept>

<Concept name="Waiting for async UI: findBy and waitFor" id="async">

After a click that starts a fetch, the result isn't there yet. **`findBy…`** queries retry until the element appears (default: up to 1 second), returning a promise:

```jsx file=Products.test.jsx
test("shows the products after loading", async () => {
  render(<ProductList />);
  expect(screen.getByText("Loading…")).toBeInTheDocument();
  expect(await screen.findByRole("heading", { name: "Tea" })).toBeInTheDocument();
  expect(screen.queryByText("Loading…")).not.toBeInTheDocument();
});
```

`waitFor(() => expect(…))` retries any assertion until it passes; use it when there's no element to find (`await waitFor(() => expect(save).toHaveBeenCalled())`). Don't wrap `getBy` calls in `waitFor` when a `findBy` would do.

</Concept>

<Concept name="jest-dom matchers" id="jest-dom">

| Matcher | Checks |
| --- | --- |
| `toBeInTheDocument()` | the element is on the page |
| `toBeVisible()` | it's visible (not hidden by CSS or `hidden`) |
| `toBeDisabled()` / `toBeEnabled()` | form controls |
| `toHaveValue("tea")` / `toBeChecked()` | inputs and checkboxes |
| `toHaveTextContent("3 items")` | text inside an element |
| `toHaveAttribute("aria-expanded", "true")` | attributes |
| `toHaveFocus()` | focus |
| `toHaveAccessibleName("Close")` | the accessible name |

They read like the requirement and give clear failure messages.

</Concept>

<HowItWorks title="Why act() warnings appear">

React batches updates and runs effects asynchronously. Testing Library wraps `render`, `fireEvent`, user-event and `findBy`/`waitFor` in **`act()`**, which makes React finish its work before your assertion. If a state update happens *outside* those (a promise resolving after the test moved on), React warns: "An update was not wrapped in act(…)". The fix is almost always to **wait for the result** with `findBy` or `waitFor`, not to call `act` yourself.

</HowItWorks>

`Newsletter` takes a `subscribe(email)` function (async). The button is disabled while the email is empty; submitting calls `subscribe` with the email and, once it resolves, shows **Thanks for subscribing!** in a status message. Write tests that catch every buggy version.

```jsx code file=/Newsletter.js
import { useState } from "react";

export default function Newsletter({ subscribe }) {
  const [email, setEmail] = useState("");
  const [status, setStatus] = useState("idle");

  async function handleSubmit(e) {
    e.preventDefault();
    setStatus("saving");
    await subscribe(email);
    setStatus("done");
  }

  if (status === "done") return <p role="status">Thanks for subscribing!</p>;
  return (
    <form onSubmit={handleSubmit}>
      <label>
        Email <input type="email" value={email} onChange={(e) => setEmail(e.target.value)} />
      </label>
      <button disabled={!email || status === "saving"}>
        {status === "saving" ? "Subscribing…" : "Subscribe"}
      </button>
    </form>
  );
}
```

```jsx starter file=/Newsletter.test.js
import { fireEvent, render, screen } from "@testing-library/react";
import "@testing-library/jest-dom";
import { expect, test, vi } from "vitest";
import Newsletter from "./Newsletter";

test("has an email field", () => {
  render(<Newsletter subscribe={vi.fn()} />);
  expect(screen.getByLabelText("Email")).toBeInTheDocument();
});
```

```jsx solution file=/Newsletter.test.js
import { fireEvent, render, screen } from "@testing-library/react";
import "@testing-library/jest-dom";
import { expect, test, vi } from "vitest";
import Newsletter from "./Newsletter";

test("the button is disabled until an email is typed", () => {
  render(<Newsletter subscribe={vi.fn()} />);
  expect(screen.getByRole("button", { name: "Subscribe" })).toBeDisabled();
  fireEvent.change(screen.getByLabelText("Email"), { target: { value: "ada@example.com" } });
  expect(screen.getByRole("button", { name: "Subscribe" })).toBeEnabled();
});

test("subscribes with the email and says thanks", async () => {
  const subscribe = vi.fn().mockResolvedValue();
  render(<Newsletter subscribe={subscribe} />);
  fireEvent.change(screen.getByLabelText("Email"), { target: { value: "ada@example.com" } });
  fireEvent.click(screen.getByRole("button", { name: "Subscribe" }));
  expect(subscribe).toHaveBeenCalledWith("ada@example.com");
  expect(await screen.findByRole("status")).toHaveTextContent("Thanks for subscribing!");
});
```
