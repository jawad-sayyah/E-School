**Coverage** measures which lines of your code ran during the tests. It's a useful map of what's *not* tested, and a misleading score if you treat it as "how good are my tests".

<Concept name="Generating a report" id="report">

```bash file=terminal
npx vitest run --coverage
```

```text file=terminal
 % Coverage report from v8
-----------------|---------|----------|---------|---------|-------------------
File             | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s
-----------------|---------|----------|---------|---------|-------------------
All files        |   87.50 |    75.00 |     100 |   87.50 |
 cartReducer.js  |   92.30 |    83.33 |     100 |   92.30 | 18
 discount.js     |   75.00 |    50.00 |     100 |   75.00 | 6-7
-----------------|---------|----------|---------|---------|-------------------
```

Vitest also writes an HTML report (`coverage/index.html`) where uncovered lines are highlighted red and partly covered branches yellow.

| Column | Counts |
| --- | --- |
| **Statements** | every statement that ran |
| **Branches** | each side of every `if`, ternary, `&&`, `??`, `switch` case |
| **Functions** | functions called at least once |
| **Lines** | lines with at least one statement that ran |

**Branches** is usually the most telling: 50% on `discount.js` means some `if` only ever went one way in the tests.

</Concept>

<Concept name="Why 100% isn't the goal" id="not-100">

Coverage tells you code **ran**, not that anything **checked** it:

```js file=useless.test.js
test("covers the whole function", () => {
  discount(150);   // runs every line of the happy path… and asserts nothing
});
```

That test raises coverage and catches no bugs. Chasing 100% leads to tests like it, plus tests for trivial code, written to please a number. Healthier habits:

- read the report for **untested important logic** (an uncovered error branch in checkout is worth a test; an uncovered `console.log` isn't);
- set a reasonable **threshold** (say 80%) in CI so coverage doesn't silently drop;
- judge tests by whether they **catch bugs**: exactly what the Write the tests exercises measure.

</Concept>

<HowItWorks title="How coverage is measured">

The **v8** provider (Vitest's default) asks the JavaScript engine itself which code ran, so it's fast and needs no changes to your code. The **istanbul** provider instead rewrites your code with counters before running it. Either way, the numbers mean "executed", which is why a test without assertions can reach 100%. Tools like **mutation testing** (Stryker) go further: they introduce small bugs on purpose and check whether your tests notice, the same idea as this course's hidden buggy versions.

</HowItWorks>
