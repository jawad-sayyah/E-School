You've seen the render cycle: **trigger → render → commit**. This lesson looks closely at each step, because almost every "why did that happen?" question in React comes down to it.

<Concept name="What triggers a render" id="triggers">

A component renders when:

1. **The app starts** (the initial render, from `root.render(<App />)`).
2. **Its state changes** (a `set` function is called with a new value).
3. **Its parent renders.** By default, when a component renders, React renders **all of its children** too, whether their props changed or not.
4. **A context it reads changes** (Hooks course).

Props changing is *not* a separate trigger: props only change because the parent rendered.

</Concept>

<Concept name="Children render with their parent" id="children-render">

<Concept name="Reconciliation: same type, same position, same state" id="reconciliation">

After rendering, React compares the new element tree with the previous one, node by node. This is **reconciliation**. The rules are simple:

- **Same type at the same position** (`<Counter />` where there was a `<Counter />`): React keeps the existing component, its DOM and its **state**, and updates the props.
- **Different type** (a `<Counter />` where there was a `<p>`, or `<div>` → `<section>`): React destroys the old subtree, **state included**, and builds the new one from scratch.
- **Different key**: treated as a different component, so it's rebuilt with fresh state.

Click + a few times on each counter, then tick the box.

<ReactPlayground height={360}>

```jsx file=/App.js
import { useState } from "react";

function Counter({ label }) {
  const [count, setCount] = useState(0);
  return (
    <p>
      {label}: {count} <button onClick={() => setCount(count + 1)}>+</button>
    </p>
  );
}

export default function App() {
  const [vip, setVip] = useState(false);
  return (
    <>
      <label>
        <input type="checkbox" checked={vip} onChange={(e) => setVip(e.target.checked)} /> VIP customer
      </label>

      {/* Same type, same position: state survives, only the label changes */}
      {vip ? <Counter label="VIP coffees" /> : <Counter label="Coffees" />}

      {/* Different type at this position: the counter is destroyed and rebuilt */}
      {vip ? <section><Counter label="Teas" /></section> : <div><Counter label="Teas" /></div>}
    </>
  );
}
```

</ReactPlayground>

The coffee counter keeps its number: React sees a `Counter` at the same spot both times, even though the JSX is written twice. The tea counter resets, because its parent switched from `<div>` to `<section>`.

</Concept>

<Concept name="Resetting state on purpose with a key" id="key-reset">

Sometimes you **want** fresh state, like a form that should clear when you switch to another customer. Give the component a `key` that changes:

```jsx file=App.jsx
<OrderForm key={customer.id} customer={customer} />
```

When `customer.id` changes, React sees a different key, throws away the old form (and everything typed in it) and mounts a new one.

</Concept>

<HowItWorks title="Is this the virtual DOM?">

"Virtual DOM" is the popular name for the element tree your components return: plain objects describing the UI. React keeps the previous tree, compares it with the new one (reconciliation), and applies the smallest set of DOM changes during the commit.

A full comparison of two trees would be slow, so React uses two shortcuts that make it fast enough for real apps:

1. **Different types produce different trees**: React doesn't try to match a `<div>` with a `<section>`; it rebuilds.
2. **Keys** tell React which children in a list match up, so it can move items instead of rebuilding them.

That's why the rules above exist, and why keys and stable component types matter so much.

</HowItWorks>

<GoDeeper title="Render phase vs. commit phase">

- **Render phase:** React calls your components. This must be **pure**: same props and state in, same JSX out, no side effects (no changing variables outside, no fetching, no DOM changes). React may call your component several times, pause, or throw the result away.
- **Commit phase:** React applies the DOM changes, updates refs, then runs effects (`useLayoutEffect` before the browser paints, `useEffect` after). This is where side effects belong.

React 18+ can also **interrupt** a render that's in progress to handle something more urgent (like typing), thanks to concurrent rendering. Pure components are what make that safe.

</GoDeeper>

Type a note for Ada, then switch to Grace: Ada's note is still there. Make the note start empty whenever the selected customer changes, **without** adding any new state or effects.

```jsx starter file=/App.js
import { useState } from "react";

const customers = [
  { id: "c1", name: "Ada" },
  { id: "c2", name: "Grace" },
];

function NoteForm({ customer }) {
  const [note, setNote] = useState("");
  return (
    <label>
      Note for {customer.name}{" "}
      <input value={note} onChange={(e) => setNote(e.target.value)} />
    </label>
  );
}

export default function App() {
  const [selected, setSelected] = useState(customers[0]);
  return (
    <>
      {customers.map((c) => (
        <button key={c.id} onClick={() => setSelected(c)}>
          {c.name}
        </button>
      ))}
      <NoteForm customer={selected} />
    </>
  );
}
```

```jsx tests file=/App.test.js
import { fireEvent, render, screen } from "@testing-library/react";

test("the note can be typed", () => {

test("switching customers starts with an empty note", () => {
  render(<App />);
  fireEvent.change(screen.getByLabelText(/Note for Ada/), { target: { value: "Oat milk" } });
  fireEvent.click(screen.getByRole("button", { name: "Grace" }));
  expect(screen.getByLabelText(/Note for Grace/)).toHaveValue("");
});
```
