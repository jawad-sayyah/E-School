An order is always in one of a few states: placed, paid, shipped, delivered. TypeScript has two ways to name such a fixed set: **enums**, and **unions of literal types**. You'll meet both in real code.

<Concept name="Enums" id="enums">

<TSPlayground file="status.ts" errors={[13]} expected={["shipped", "Shipped orders: 1"]}>

```ts
enum OrderStatus {
  Placed = "placed",
  Paid = "paid",
  Shipped = "shipped",
}

const orders = [
  { id: 1, status: OrderStatus.Paid },
  { id: 2, status: OrderStatus.Shipped },
];

console.log(OrderStatus.Shipped);
const typo: OrderStatus = "shipped";     // error: a plain string isn't an OrderStatus
console.log("Shipped orders:", orders.filter((o) => o.status === OrderStatus.Shipped).length);
```

</TSPlayground>

- Members are used as `OrderStatus.Shipped`, which reads well and autocompletes.
- Give enums **string values** (`= "shipped"`): they're readable in logs and APIs. Without them, members are numbered 0, 1, 2…, and any number is accepted.
- Unlike almost everything else in TypeScript, an enum **exists at run time**: it compiles to a real object.

</Concept>

<Concept name="The alternatives: literal unions and as const objects" id="alternatives">

```ts file=status.ts
// 1. A union of string literals: no run-time code at all
type OrderStatus = "placed" | "paid" | "shipped";
const s: OrderStatus = "paid";                 // plain strings, still checked

// 2. An object as const, when you also want the values at run time (to loop over, say)
const ORDER_STATUS = {
  Placed: "placed",
  Paid: "paid",
  Shipped: "shipped",
} as const;
type Status = (typeof ORDER_STATUS)[keyof typeof ORDER_STATUS]; // "placed" | "paid" | "shipped"

Object.values(ORDER_STATUS);                   // ["placed", "paid", "shipped"]
```

Many teams prefer these:

- they're **plain JavaScript values**: data from an API (`"paid"`) fits directly, no conversion;
- they produce **no extra code** (the union) or obvious code (the object);
- newer tools that just strip types (Node's built-in TypeScript support, the `erasableSyntaxOnly` option) don't support enums, because enums need real code generated.

Use whichever your codebase uses. For new code, a literal union is a great default.

</Concept>

<HowItWorks title="What an enum compiles to">

A string enum becomes an object:

```js file=status.js
var OrderStatus;
(function (OrderStatus) {
  OrderStatus["Placed"] = "placed";
  OrderStatus["Paid"] = "paid";
  OrderStatus["Shipped"] = "shipped";
})(OrderStatus || (OrderStatus = {}));
```

A numeric enum also gets a **reverse mapping** (`OrderStatus[0] === "Placed"`). This generated code is why enums are the one TypeScript feature that isn't "JavaScript plus erasable types".

</HowItWorks>

<TSExercise
  id="size-union"
  title="Sizes as a union, prices as a record"
  hints={[
    "`type Size = \"small\" | \"medium\" | \"large\";`",
    "Annotate the prices object so every size must have a number: `const PRICES: { [S in Size]: number } = { … }` (or `Record<Size, number>`, coming next course).",
    "`function price(size: Size): number { return PRICES[size]; }`",
  ]}
>

Replace the loose `string` with a `Size` union of `"small"`, `"medium"` and `"large"`, make sure `PRICES` has a number for **every** size, and type `price` to take a `Size`.

```ts starter
type Size = string;

const PRICES = { small: 3.5, medium: 4.5, large: 5 };

function price(size) {
  return PRICES[size];
}
```

```ts types
const m: number = price("medium");
// @ts-expect-error only the three sizes exist
price("huge");
// @ts-expect-error a Size is one of the three strings
const s: Size = "extra large";
```

```js tests
test("looks up the price of each size", () => {
  expect(price("small")).toBe(3.5);
  expect(price("large")).toBe(5);
});
```

```ts solution
type Size = "small" | "medium" | "large";

const PRICES: { [S in Size]: number } = { small: 3.5, medium: 4.5, large: 5 };

function price(size: Size): number {
  return PRICES[size];
}
```

</TSExercise>
