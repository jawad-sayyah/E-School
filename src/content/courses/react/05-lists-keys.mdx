Most UIs show lists: products, cart lines, messages. In React you turn an **array of data** into an **array of elements** with `.map()`, and give each element a `key`.

<Concept name="Rendering a list" id="render-list">

<ReactPlayground height={340}>

```jsx file=/App.js
const products = [
  { id: "p1", name: "Coffee", price: 4, hot: true },
  { id: "p2", name: "Iced Tea", price: 3, hot: false },
  { id: "p3", name: "Hot Chocolate", price: 5, hot: true },
  { id: "p4", name: "Lemonade", price: 3, hot: false },
];

export default function App() {
  const hotDrinks = products.filter((p) => p.hot);

  return (
    <>
      <h2>All drinks</h2>
      <ul>
        {products.map((p) => (
          <li key={p.id}>
            {p.name}: ${p.price}
          </li>
        ))}
      </ul>
      <h2>Hot drinks ({hotDrinks.length})</h2>
      <ul>
        {hotDrinks.map((p) => (
          <li key={p.id}>{p.name}</li>
        ))}
      </ul>
    </>
  );
}
```

</ReactPlayground>

- `products.map(...)` returns an array of `<li>` elements, and JSX renders arrays in order.
- Filter (or sort) first, then map. Derived lists like `hotDrinks` are plain variables, not state.
- Every element in the array gets a **`key`** that's unique among its siblings.

</Concept>

<Concept name="Why keys matter" id="why-keys">

Keys tell React **which item is which** between renders. Without them (or with the array index), React matches items by position, and anything attached to an element, like typed text or focus, stays at that position even when the data moves.

Type a note next to **Coffee** in both lists, then click **Add Tea to the top**.

<ReactPlayground height={420}>

```jsx file=/App.js
import { useState } from "react";

function OrderList({ title, items, useIndexKey }) {
  return (
    <section>
      <h3>{title}</h3>
      {items.map((item, index) => (
        <p key={useIndexKey ? index : item.id}>
          {item.name} <input placeholder="Note" />
        </p>
      ))}
    </section>
  );
}

export default function App() {
  const [items, setItems] = useState([
    { id: 1, name: "Coffee" },
    { id: 2, name: "Bagel" },
  ]);

  function addTea() {
    setItems([{ id: Date.now(), name: "Tea" }, ...items]);
  }

  return (
    <>
      <button onClick={addTea}>Add Tea to the top</button>
      <OrderList title="key={index} (broken)" items={items} useIndexKey />
      <OrderList title="key={item.id} (correct)" items={items} />
    </>
  );
}
```

</ReactPlayground>

With `key={index}`, the new Tea row takes key `0`, which used to be Coffee's, so it inherits Coffee's input and your note jumps to Tea. With `key={item.id}`, React knows Coffee simply moved down, and the note moves with it.

</Concept>

<Concept name="Rules for keys" id="key-rules">

- **Unique among siblings.** Two lists can reuse the same keys; items in one list can't.
- **Stable.** The same item must get the same key on every render. Use an id from your data (a database id, a product SKU).
- **Never `Math.random()` or `Date.now()` in render.** A new key every render means React destroys and rebuilds every item each time.
- **The index is only OK** when the list never reorders, filters or inserts, and items have no state.
- The key goes on the **outermost element** returned from `map`. If that's a fragment, use the long form: `<Fragment key={id}>`.

<Callout type="tip">
`key` isn't a normal prop: the child component can't read `props.key`. If the child needs the id, pass it separately too: `<CartLine key={line.id} id={line.id} />`.
</Callout>
</Concept>

<HowItWorks title="Keys and reconciliation">

After each render, React compares the new list of children with the old one. Children with the **same key** (and the same type) are treated as the same item: React keeps its DOM node and its state, and only updates what changed. Keys that disappeared are removed; new keys are created. Without keys React can only compare by position, so inserting at the top looks like "every item changed, plus one new at the end".

This comparison is called **reconciliation**, and How React Works covers it in depth.

</HowItWorks>
