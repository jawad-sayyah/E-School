A real app is many files: one per component, one for helpers, one for API calls. Modules connect them. These examples need a real project (with files), so they show what happens instead of running here.

<Concept name="Named exports" id="named-exports" react>

`export` in front of a function or variable makes it available to other files, which import it by its exact name in `{ }`.

<Playground
  file="cart.js"
  browserOnly
  expected={["~ cart.js shares two things; App.js imports them by name.", "[ { name: 'Coffee' } ] 0.16"]}
>

```js
// cart.js
export function addItem(cart, item) {
  return [...cart, item];
}
export const TAX = 0.16;

// App.js
import { addItem, TAX } from "./cart.js";

console.log(addItem([], { name: "Coffee" }), TAX);
```

</Playground>
</Concept>

<Concept name="Default export" id="default-export" react>

A file can have one `export default`. You import it without `{ }`, and you can give it any name.

<Playground
  file="Cart.jsx"
  browserOnly
  expected={["~ Both imports get the same function: the name is up to you."]}
>

```js
// Cart.jsx
export default function Cart() {
  /* ... */
}

// App.jsx
import Cart from "./Cart.jsx";
import ShoppingCart from "./Cart.jsx";   // also works
```

</Playground>

<Callout type="react">
Most React projects use one component per file with `export default`, and named exports for helpers and hooks.
</Callout>
</Concept>

<Concept name="Default + named together" id="default-and-named">

One import line can take the default export and named exports at the same time.

<Playground
  file="App.js"
  browserOnly
  expected={["~ Nothing to print: this connects files together."]}
>

```js
// cart.js
export function addItem(item) { /* ... */ }
export default function Cart() { /* ... */ }

// App.js
import Cart, { addItem } from "./cart.js";
```

</Playground>
</Concept>

<Concept name="as" id="import-as">

`as` renames an import, which helps when two files export the same name.

<Playground
  file="rename.js"
  browserOnly
  expected={["~ Two different formatPrice functions, no name clash."]}
>

```js
import { formatPrice } from "./cart.js";
import { formatPrice as formatEuro } from "./euro.js";

formatPrice(4);   // "$4.00"
formatEuro(4);    // "4,00 €"
```

</Playground>
</Concept>

<Concept name="Module scope" id="module-scope">

Variables in a module are private to that file unless you export them, so files can't clash by accident.

<Playground
  file="counter.js"
  browserOnly
  expected={["~ main.js can call nextId(), but can't touch lastId."]}
>

```js
// ids.js
let lastId = 0;               // private to this file
export function nextId() {
  lastId += 1;
  return lastId;
}

// main.js
import { nextId } from "./ids.js";
nextId();   // 1
nextId();   // 2
```

</Playground>
</Concept>

<Concept name="Import mistakes" id="import-mistakes" warn>

The most common error is mixing up `{ }`: named exports need the braces, the default export must not have them.

<Compare
  wrong="Cart is undefined: there's no named export called Cart"
  right="Imports the default export"
  wrongFile="App.jsx"
  rightFile="App.jsx"
>

```js
// Cart.jsx has: export default function Cart() {}
import { Cart } from "./Cart.jsx";
```

```js
// Cart.jsx has: export default function Cart() {}
import Cart from "./Cart.jsx";
```

</Compare>
</Concept>

<GoDeeper title="What a bundler does with your imports">

Browsers can load modules directly (`<script type="module">`), but real projects use a **bundler** like Vite. It starts at your entry file, follows every `import`, and combines everything into a few optimized files. Along the way it:

- resolves bare imports like `import React from "react"` to the package in `node_modules`;
- drops exports nobody imports (**tree-shaking**), so unused code never reaches the user;
- splits code loaded with `import()` (a dynamic import) into separate chunks that download on demand.

This site works that way too: each lesson is its own chunk, loaded when you open it.

</GoDeeper>
